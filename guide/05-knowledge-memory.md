# 5. Knowledge & memory

Two things help JARVIS avoid starting from zero every time:

- **Knowledge**: what's known about a *project's code* — what each file does, its symbols, its
  dependencies, its documentation. Generated by the model from your source files.
- **Long-term memory (LTM)**: what happened in *earlier sessions* — decisions, preferences, facts,
  summaries of finished turns.

Both are injected into each agent step in small doses, and both have tools for the agent to dig
deeper.

## Knowledge

### What it's made of

Two kinds of files, one of each per source file:

**Component JSON** (task `code/extract-knowledge`): a structured summary.

```json
{
  "component": { "name": "memory_manager", "source_path": "ai/agents/memory_manager.py",
                 "doc_path": "ai/agents/memory_manager.md", "type": "module" },
  "vector_memory": { "semantic_summary": "Per-agent memory: messages, history, notes ..." },
  "graph_nodes": [ { "id": "MemoryManager", "label": "class", "signature": "class MemoryManager(...)" } ],
  "graph_edges": [ { "source": "MemoryManager", "target": "ai/agents/agent_io.py", "relation": "depends_on" } ],
  "metadata": { "environment_variables": [], "external_dependencies": ["json"], "has_side_effects": false }
}
```

Only `component.source_path` is required; unknown fields are kept.

**Markdown doc** (task `code/create-code-documentation`): a readable page per file (overview,
public API, implementation details, dependencies). It's split by headings into sections for
search, and linked to its component through the path.

Paths are matched loosely: `ai/agents/memory_manager.py`, `/ai/agents/memory_manager.md` and
`ai\agents\memory_manager` are the same key.

This repo's own knowledge is in `_knowledge/` (JSON) and `_docs/` (Markdown).

### Building it

```bash
./run.sh knowledge build                         # this folder: src/ (or .), only new/changed files
./run.sh knowledge build src --ext py,ts      # source root, only these extensions
./run.sh knowledge build --ext all            # back to every text file (forgets saved extensions)
./run.sh knowledge build --mode all           # regenerate everything
./run.sh knowledge build --mode diff:master   # files changed vs a branch
./run.sh knowledge build --files src/app/main.py --only knowledge
./run.sh knowledge list                          # what's registered here, and coverage
```

It makes **one model call per file and kind** (docs first, then knowledge, with the doc as extra
context). Use a model with a big enough context window for your largest files.

| Option | Default | Description |
|--------|---------|-------------|
| `SRC` (after `ai knowledge build`) | `src/` if it exists, else `.` | Source root. |
| `--mode` | `changed` | `missing` (never built or failed), `changed` (also files whose content changed), `all`, `diff[:branch]` (changed vs a git branch, default `master`). |
| `--only` | both | `docs` or `knowledge`. |
| `--ext` | the last build's, then `KNOWLEDGE_EXTENSIONS`, then every text file | Extensions, comma separated, or `all`. |
| `--files` | — | Only these files, comma separated. |
| `--max` | no limit | Stop after N files. |
| `--force` | off | Regenerate files that are up to date. |

**Output:** `<root>/knowledge/<project>-<hash>/docs/` and `.../knowledge/`, mirroring the source
tree (`KNOWLEDGE_OUTPUT_DIR` changes the base). A `.state.json` in each keeps the hash and status of
every source file, so `changed` needs no git and failed files are retried next time. Folders like
`.git`, `node_modules`, `.venv`, `dist` and `build` are skipped.

**Which files.** Without `--ext` (and with nothing saved or configured), every text file is
documented, except: hidden files and folders, files git ignores, binaries (images, fonts,
archives, compiled files, or any file with a null byte), lockfiles (`package-lock.json`,
`poetry.lock`, ...), minified files and source maps, and files over 256 KB. The extensions of a
build are saved for the project, so the next build uses the same ones; `--ext all` goes back to
every file.

When two files share a name without extension (`card.component.ts` and `card.component.html`),
their outputs keep the full name (`card.component.ts.md`, `card.component.html.md`) so one doesn't
overwrite the other.

The list of related project files is sent with each call, so dependency edges and doc links point
at real files.

### Sources and the per-project registry

A **source** is a folder of component JSON and/or Markdown docs. Each project folder remembers its
sources in `<root>/system/knowledge/projects.json`, so you only add them once:

- folders built with `ai knowledge build` are registered automatically;
- `ai agent --knowledge PATH` (repeatable) adds an existing folder, e.g. one you generated elsewhere;
- the agent tool `ingest_knowledge` and the server API can add sources too.

```bash
./run.sh agent --knowledge ./_knowledge --knowledge ./_docs   # once; remembered for this folder
./run.sh knowledge list                                       # sources, build settings, coverage
./run.sh knowledge forget ID                                  # stop loading one
```

More ways to add sources:
- `KNOWLEDGE_SOURCES` in `config.json`: loaded for **every** project. Paths, or
  `{"id": "...", "path": "...", "kind": "auto|knowledge|docs"}` (`auto` detects the kind).
- `"knowledge": [...]` at the top of a pipeline: extra sources for that pipeline.
- `"knowledge": ["id", ...]` on an agent in a pipeline: that agent **only** sees those sources.

### How agents use it

**Automatically, each step**, the payload gets a short, budgeted slice (`KNOWLEDGE_INJECT_TOP_K`
items, `KNOWLEDGE_INJECT_MAX_CHARS` characters):
- `relevant_components` — components matching the current task;
- `related_to_touched_files` — neighbours of the files the agent just read or changed.

It's recomputed only when the task or the touched files change.

**With tools** (category `knowledge`):

| Tool | What it does |
|------|--------------|
| `search_knowledge` | Search components and doc sections. |
| `get_component` | Summary, symbols and dependencies of one file. |
| `knowledge_neighbors` | Files that a file depends on / that depend on it. |
| `find_symbol` | Where a class or function is defined. |
| `read_doc` | The doc of a file, or one section of it. |
| `knowledge_status` | Build coverage of the project. |
| `update_knowledge` | Generate or refresh knowledge for some files. |
| `ingest_knowledge` | Register a knowledge/docs folder for this project. |

**Search** combines a keyword index (BM25) with semantic search (embeddings in ChromaDB) when the
vector engine is installed, merged by rank. The semantic index is built in the background; keyword
search is used until it's ready, or when the engine isn't installed (`KNOWLEDGE_SEMANTIC`).

### Keeping it up to date

When an agent changes a file (`write_file`, `patch_file`, `delete_file`), that file's knowledge is
marked stale. At the end of the turn, if the project's knowledge was built by the app, the changed
files are regenerated (`KNOWLEDGE_AUTO_UPDATE`, up to `KNOWLEDGE_AUTO_UPDATE_MAX` files per turn).
For bigger changes, run `ai knowledge build` again (the default `changed` mode only redoes what
changed).

## Long-term memory

LTM is a vector database (ChromaDB, embeddings from `all-MiniLM-L6-v2` via sentence-transformers).
It's on when its engine is installed (`./run.sh install` → Long Term Memory); set
`VECTOR_MEMORY_ENABLED: false` to turn it off.

**What gets stored:**

| Type | Stored when | Importance |
|------|-------------|------------|
| `decision`, `user_preference` | The agent calls `remember` | 8 |
| `reflection` | A reflection distils recent memories | 7 |
| `fact` | `remember` | 6 |
| `episode` | Every finished agent turn: what it was about and how it ended (no extra model call) | 6 |
| `distilled_observation` | The Context Sentinel summarized a large tool result | 5 |
| `observation`, `communication` | Other agent notes | 5, 4 |
| `chat_turn` | Each message in plain chat mode | 3 |

Importance comes from the type, unless `LTM_LLM_IMPORTANCE` asks the model to rate each memory
(one extra call per memory, slower).

**Scope** (`LTM_SCOPE`) decides which memory a run reads and writes:
- `project` (default): one memory per folder, shared by all its sessions;
- `session`: one memory per session;
- `global`: one memory for everything.

**Recall.** Each agent step gets up to `LTM_INJECT_TOP_K` memories relevant to the task as
`long_term_memory`, if their similarity is at least `LTM_MIN_RELEVANCE` (decisions and preferences
are favoured). The agent can also call `query_memory`. Memories are ranked by
`relevance + importance + recency`, each weighted by `VECTOR_*_WEIGHT` (all `1.0`).

**Reflection.** When a run ends with at least `LTM_AUTO_REFLECT_MIN` new memories, one model call
turns the recent ones into a few higher-level insights (`reflection`). Agents can trigger it with
`trigger_reflection`.

**Where:** `<root>/databases/` (`VECTOR_DB_PATH`), one collection per scope.

## Settings

| Setting | Default | Description |
|---------|---------|-------------|
| `KNOWLEDGE_ENABLED` | `true` | Knowledge module. |
| `KNOWLEDGE_SOURCES` | `[]` | Sources for every project. |
| `KNOWLEDGE_OUTPUT_DIR` | `<root>/knowledge` | Base folder for generated knowledge. |
| `KNOWLEDGE_EXTENSIONS` | every text file | Extensions `ai knowledge build` documents (saved per project once built). `["all"]` = every text file. |
| `KNOWLEDGE_AUTO_UPDATE` / `_MAX` | `true` / `5` | Regenerate changed files at the end of a turn. |
| `KNOWLEDGE_SEMANTIC` | engine installed | Embedding search for knowledge. |
| `KNOWLEDGE_INJECT_TOP_K` / `_MAX_CHARS` | `4` / `1500` | Knowledge added per step (0 = off). |
| `VECTOR_MEMORY_ENABLED` | engine installed | Long-term memory. |
| `VECTOR_DB_PATH` | `<root>/databases` | Memory database folder. |
| `LTM_SCOPE` | `project` | `project`, `session` or `global`. |
| `LTM_INJECT_TOP_K` / `LTM_MIN_RELEVANCE` | `4` / `0.3` | Memories added per step. |
| `LTM_AUTO_REFLECT_MIN` | `15` | New memories that trigger a reflection (0 = off). |
| `LTM_LLM_IMPORTANCE` | `false` | Model rates each memory. |
| `VECTOR_RECENCY_WEIGHT` / `_IMPORTANCE_` / `_RELEVANCE_` | `1.0` | Ranking weights. |

## Server API

The Brain Server exposes the knowledge too (see [Server](07-server.md#api-overview)):

| Endpoint | Description |
|----------|-------------|
| `GET /api/v1/knowledge/sources` | Registered sources. |
| `POST /api/v1/knowledge/sources` / `DELETE .../sources/{id}` | Add / remove a source. |
| `GET /api/v1/knowledge/search` | Search. |
| `GET /api/v1/knowledge/component` | One component. |
| `GET /api/v1/knowledge/status` | Build coverage. |
| `POST /api/v1/knowledge/build` | Start a build in the background (one at a time; not while an agent run is active). |
| `GET .../build/{job_id}`, `POST .../build/{job_id}/cancel` | Follow / cancel a build. |
